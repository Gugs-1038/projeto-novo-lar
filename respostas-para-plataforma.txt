5. MENU DROPDOWN E HAMBÚRGUER

A navegação foi construída com os seletores .cabecalho, .navegacao, .menu, .item-com-submenu e .submenu. Em telas maiores, o submenu de Projetos permanece recolhido com opacity: 0, visibility: hidden e pointer-events: none. O JavaScript abre o conteúdo ao alterar aria-expanded para true, acionando o seletor .controle-submenu[aria-expanded="true"] + .submenu. A transição combina opacity e transform para tornar a abertura mais suave.

No breakpoint @media (max-width: 768px), o botão .controle-menu é exibido e o menu passa a ser vertical. A navegação fechada utiliza max-height: 0, opacity: 0, visibility: hidden e overflow: hidden. Quando aria-expanded recebe true, o seletor .controle-menu[aria-expanded="true"] + .navegacao revela os links e transforma as três linhas do ícone em um X.

Foram usados elementos button para permitir a operação por teclado e tecnologias assistivas. O menu também pode ser fechado com a tecla Esc, por clique fora do cabeçalho ou após a escolha de um link. A regra prefers-reduced-motion desativa as transições para pessoas sensíveis a movimento. Se o JavaScript não carregar, a navegação continua visível para que nenhum link fique inacessível.

6. ESTADOS INTERATIVOS E VALIDAÇÃO VISUAL

Nos botões, a classe .botao possui transições de 0.2s para cores, borda, sombra e opacidade, além de 0.1s para o deslocamento. Em :hover, o fundo passa para a cor de destaque, a borda acompanha essa cor, surge uma pequena sombra e o botão sobe 2px. Em :focus-visible, aparecem um anel amarelo e um contorno verde-escuro, deixando claro qual controle está selecionado pelo teclado. Em :active, a sombra diminui e o botão desce 1px, simulando o toque. Já :disabled utiliza fundo neutro, opacidade de 60%, cursor not-allowed e retira a sombra e o deslocamento.

Os controles do menu também escurecem em :hover e diminuem levemente em :active. Nos cartões, :hover e :focus-within reforçam a borda, acrescentam sombra e elevam o bloco em 3px. Assim, a resposta visual não depende apenas do uso do mouse, pois também aparece quando um link interno recebe foco pelo teclado.

No formulário, os campos usam uma transição suave para fundo, borda e sombra. Em :hover, a borda fica verde-escura e, em :focus-visible, surge um anel de foco. Depois da interação, o JavaScript alterna .campo-valido e .campo-invalido: o primeiro aplica fundo verde-claro, borda verde e uma mensagem de confirmação; o segundo usa fundo avermelhado, borda vermelha e uma orientação específica. A mensagem é um elemento small real, ligado ao campo por aria-describedby. As pseudo-classes :user-valid e :user-invalid permanecem como alternativa quando o JavaScript não carrega. A regra prefers-reduced-motion remove transições e deslocamentos para quem prefere menos animações.

8. SINGLE PAGE APPLICATION E MANIPULAÇÃO DO DOM

Adotei o roteamento por hash com as rotas #/inicio, #/projetos e #/cadastro. Também foram criadas subrotas para resgate, voluntariado e doações. Essa escolha permite que o Projeto Novo Lar funcione como uma Single Page Application em hospedagem estática, sem exigir configurações especiais no servidor. Cada alteração do hash fica registrada no histórico, mantendo o funcionamento dos botões Voltar e Avançar.

Os links internos possuem o atributo data-rota, mas conservam endereços HTML reais no href como alternativa caso o JavaScript não carregue. Um listener central identifica somente esses links, usa preventDefault() e atualiza location.hash. Links de e-mail, telefone, downloads ou externos não são interceptados.

Trecho principal:

document.addEventListener("click", (evento) => {
  const link = evento.target.closest("a[data-rota]");
  if (!link) return;
  evento.preventDefault();
  window.location.hash = link.dataset.rota;
});

window.addEventListener("hashchange", () => renderizarRota());

function renderizarRota() {
  const rotaSolicitada = obterRota();
  const nomeRota = rotaSolicitada.desconhecida ? "inicio" : rotaSolicitada.nome;
  const configuracao = rotas[nomeRota];
  conteudo.className = configuracao.classe;
  conteudo.replaceChildren(criarFragmento(configuracao));
  document.title = configuracao.titulo;
  atualizarNavegacao(nomeRota);
}

A função real do projeto interpreta o hash, escolhe a configuração correspondente e cria um fragmento a partir do conteúdo inicial ou de elementos template. O método replaceChildren() remove o conteúdo anterior do main#conteudo antes de inserir o novo fragmento. Desse modo, as páginas não se acumulam e os identificadores não ficam duplicados no DOM ativo.

Após a renderização, também são atualizados o título do documento, a meta description, o aria-current do menu e uma região de status para leitores de tela. Nas subrotas, o foco é levado ao título da secção solicitada. O formulário utiliza delegação de eventos no document, permitindo que validação, alerta e toast continuem funcionando mesmo quando o Cadastro é inserido dinamicamente.

Mantive o cabeçalho, o menu e o rodapé como estrutura fixa. Apenas o conteúdo central é substituído, oferecendo uma navegação rápida, histórico funcional e gerenciamento de foco sem retirar as alternativas estáticas para quem estiver sem JavaScript.

9. SISTEMA DE TEMPLATES E COMPONENTES DINÂMICOS

No Projeto Novo Lar, usei o elemento HTML5 template para manter uma única estrutura reutilizável para os cartões de Voluntariado e Doações. Os conteúdos ficam separados no array dadosAcoes. Cada objeto reúne categoria, título, descrição, badges, itens e link de ação, sem repetir toda a marcação HTML.

Quando a rota de Projetos é exibida, o JavaScript percorre o array com forEach. Para cada objeto, a função criarCartao() copia o modelo com cloneNode(true), localiza os campos pelos atributos data-campo e insere os textos com textContent. As badges e os itens das listas são criados com document.createElement().

Trecho principal:

const lote = document.createDocumentFragment();

dadosAcoes.forEach((dados) => {
  const cartao = criarCartao(dados, modelo);
  lote.append(cartao);
});

lista.replaceChildren(lote);

O DocumentFragment reúne todos os cartões antes da inserção. Assim, o DOM é atualizado de uma só vez, deixando a renderização mais organizada. O uso de textContent, em vez de innerHTML, impede que os dados sejam interpretados como marcação e reduz o risco de inserir código indevido. Para criar um novo cartão, basta adicionar outro objeto ao array; a estrutura, as classes e os atributos acessíveis continuam sendo aplicados pelo mesmo template.

10. VERIFICAÇÃO DE CONSISTÊNCIA DO FORMULÁRIO

No Projeto Novo Lar, centralizei a verificação nas funções validarCampo() e validarFormulario(). Todos os campos são obrigatórios e valores formados apenas por espaços são rejeitados com trim(). Nome, endereço e cidade também possuem tamanhos mínimos. O e-mail utiliza type="email" e a propriedade validity.typeMismatch, enquanto a data de nascimento recebe como limite máximo a data atual, impedindo datas futuras.

Os formatos específicos são avaliados com expressões regulares. O CPF segue /^\d{3}\.\d{3}\.\d{3}-\d{2}$/, o telefone usa /^\(\d{2}\) \d{4,5}-\d{4}$/, o CEP usa /^\d{5}-\d{3}$/ e a UF precisa corresponder a /^[A-Z]{2}$/. Além do formato, o CPF tem os dígitos verificadores calculados e a UF é comparada com a lista das unidades federativas brasileiras. Essas verificações são locais e não consultam bases externas.

Ao carregar o formulário, o script cria para cada input um elemento small com document.createElement(). Essa mensagem recebe um identificador, aria-live="polite" e é ligada ao campo por aria-describedby. O conteúdo é inserido com textContent. Conforme o resultado, o código atualiza aria-invalid e alterna as classes .campo-invalido e .campo-valido, exibindo borda, fundo e texto de orientação ou confirmação. Assim, o retorno não depende somente da cor.

No evento focusout, o campo é marcado como já utilizado e validado. Depois disso, input repete a verificação em tempo real enquanto a pessoa corrige o valor. No submit, preventDefault() impede o envio convencional, todos os campos são revisados e, se houver falhas, o alerta geral informa quantos campos precisam de correção e o foco vai para o primeiro inválido. Quando tudo está consistente, o alerta é ocultado e o toast de sucesso aparece.

Os listeners usam delegação no document e, por isso, também funcionam quando o formulário é inserido pela SPA. O JavaScript ativa noValidate apenas durante sua execução para assumir o fluxo personalizado; se o script falhar ou estiver desativado, os atributos required, type, minlength e pattern mantêm a validação nativa do navegador.

11. PERSISTÊNCIA COM LOCALSTORAGE

No Projeto Novo Lar, utilizei o localStorage somente para guardar a navegação recente. Nenhum dado pessoal do formulário — como nome, CPF, telefone, e-mail, nascimento ou endereço — é armazenado. Essa decisão protege o utilizador, pois o conteúdo do localStorage não é criptografado e pode continuar no dispositivo mesmo depois que o navegador é fechado.

As informações são organizadas em um objeto com três propriedades: versao, ultimaRota e historico. O histórico é um array limitado às oito navegações mais recentes, e cada item contém somente a rota e a data e hora do acesso. A versão permite que a estrutura seja reconhecida e atualizada com segurança no futuro.

Sempre que uma rota válida é renderizada, registrarRota() atualiza o objeto. JSON.stringify() converte a estrutura em texto e localStorage.setItem() grava o resultado na chave projeto-novo-lar:navegacao:v1. Se a nova rota for igual à última, apenas o horário é atualizado; caso contrário, uma entrada é adicionada. O uso de slice(-8) impede que o histórico cresça indefinidamente.

Na abertura da aplicação, localStorage.getItem() recupera o texto e JSON.parse() o transforma novamente em objeto. Antes de usar os dados, o código confirma a versão, verifica se ultimaRota pertence à lista de rotas permitidas e filtra o histórico para aceitar apenas itens com rota e data válidas. Quando o endereço não contém uma rota explícita, a SPA restaura a última página visitada; na ausência de dados válidos, abre /inicio.

Todas as operações ficam dentro de try/catch. Assim, JSON corrompido, armazenamento bloqueado ou falta de espaço não interrompem a aplicação. Nessas situações, o histórico é ignorado e o site continua com o comportamento padrão. Dessa forma, a persistência oferece continuidade sem guardar informações sensíveis.

12. INTEGRAÇÃO DE BIBLIOTECA EXTERNA

No Projeto Novo Lar, integrei a biblioteca IMask 7.6.1 para facilitar o preenchimento dos campos de CPF, telefone e CEP. Ela foi carregada por CDN com a versão fixada e o atributo async, enquanto o arquivo local integracoes.js usa defer. Assim, uma conexão lenta não impede que os demais recursos do site sejam executados.

As máscaras foram configuradas como 000.000.000-00 para CPF e 00000-000 para CEP. No telefone, usei uma máscara dinâmica com os formatos (00) 0000-0000 e (00) 00000-0000; a função dispatch escolhe o modelo adequado conforme a quantidade de dígitos. A inicialização fica isolada em uma IIFE no arquivo integracoes.js, evitando variáveis globais desnecessárias. Um WeakMap registra os campos já preparados e impede que a mesma máscara seja aplicada duas vezes.

Como o projeto funciona como SPA e o formulário pode ser inserido dinamicamente no DOM, a função iniciarMascaras() é chamada após o evento personalizado novolar:rota-renderizada. Ela também responde ao evento load do script externo, cobrindo o caso em que a CDN termina de carregar depois do código local. Dessa forma, os recursos são ativados sempre que a rota de cadastro é aberta, inclusive depois de outras navegações.

Antes de iniciar, o código verifica se window.IMask está disponível. Se a CDN não carregar, a aplicação continua funcionando: os campos permanecem utilizáveis e o JavaScript próprio ainda verifica obrigatoriedade, formato, dígitos do CPF, telefone e CEP. Portanto, a biblioteca melhora a experiência de digitação, mas não substitui a validação nem compromete o funcionamento principal do sistema.

13. ORGANIZAÇÃO MODULAR DO JAVASCRIPT

Organizei o JavaScript do Projeto Novo Lar em arquivos menores, cada um com uma responsabilidade bem definida. O menu.js controla o menu responsivo e os submenus; o formulario.js concentra a validação e os retornos visuais; o componentes.js gera os cartões repetitivos; o persistencia.js cuida do histórico de navegação no localStorage; o integracoes.js inicializa as máscaras de CPF, telefone e CEP; e o spa.js coordena as rotas e a troca do conteúdo principal.

Essa divisão mantém alta coesão, pois cada arquivo reúne somente funções ligadas ao mesmo objetivo, e reduz o acoplamento. Todas as implementações ficam protegidas por IIFEs, evitando que variáveis e funções internas disputem o escopo global. Quando uma função precisa ser compartilhada, o arquivo expõe apenas uma pequena API no objeto window, protegida com Object.freeze().

O spa.js, por exemplo, acessa renderizarCartoesAjuda() e as funções de persistência por meio das APIs NovoLarComponentes e NovoLarPersistencia. Usei optional chaining nessas chamadas, de modo que elas só ocorram quando o recurso estiver disponível. O roteador não precisa conhecer os detalhes internos da criação dos cartões nem do armazenamento.

Também adotei comunicação por eventos. Depois de inserir uma rota no DOM, o spa.js dispara o evento personalizado novolar:rota-renderizada. O formulario.js e o integracoes.js escutam esse aviso e preparam os elementos recém-inseridos. Dessa forma, a SPA apenas comunica que a tela mudou, sem depender diretamente da implementação desses recursos.

Os scripts locais utilizam defer, preservando a ordem declarada no HTML e aguardando a análise do documento. A biblioteca IMask usa async e possui verificação de disponibilidade e fallback, por isso seu carregamento não bloqueia os demais scripts.

Não utilizei import e export nos ficheiros fonte porque o projeto continua preparado para abrir diretamente por html/index.html, sem servidor. Na versão de produção, o esbuild reúne esses scripts em bundles minificados sem alterar a organização original de desenvolvimento. Assim, IIFEs, APIs mínimas e eventos personalizados mantêm a modularidade dos fontes, enquanto o empacotamento fica restrito à build.

14. PRINCIPAIS PROBLEMAS, DIAGNÓSTICOS E SOLUÇÕES

PROBLEMA 1

Problema:
Ao abrir o cadastro pela navegação SPA, os campos apareciam, mas a validação e as máscaras podiam não ser ativadas porque o formulário era inserido depois da carga inicial.

Técnica de diagnóstico:
Usei o console e pontos de interrupção para comparar a ordem dos eventos. A inspeção do DOM mostrou que a preparação ocorria antes de os novos campos existirem.

Solução:
Mantive os eventos de input e submit por delegação no document e passei a emitir novolar:rota-renderizada após cada troca de tela. O formulario.js e o integracoes.js escutam esse aviso e preparam os elementos recém-inseridos, mantendo os comportamentos ativos em todas as visitas ao cadastro.

PROBLEMA 2

Problema:
Em conexões lentas, a biblioteca IMask podia terminar de carregar depois do script local, deixando CPF, telefone e CEP temporariamente sem máscara.

Técnica de diagnóstico:
Simulei lentidão e falha da CDN no painel Rede e acompanhei window.IMask no console. O teste confirmou que a ordem variava conforme o tempo da requisição.

Solução:
Configurei a biblioteca com carregamento assíncrono e incluí uma verificação de disponibilidade antes da inicialização. A função também responde ao evento load da biblioteca e ao evento de mudança de rota. Se a CDN falhar, o formulário continua disponível e a validação própria permanece ativa.

PROBLEMA 3

Problema:
A primeira máscara de telefone podia posicionar o hífen incorretamente ao alternar entre números brasileiros com dez e onze dígitos.

Técnica de diagnóstico:
Testei digitação, colagem, exclusão e alternância entre dez e onze dígitos. O acompanhamento do valor no console revelou a escolha incorreta do padrão.

Solução:
Troquei o padrão único por duas máscaras, uma para telefone fixo e outra para celular. A função dispatch considera somente a quantidade de dígitos e seleciona dinamicamente o formato correto. Um WeakMap impede inicializações repetidas quando a pessoa retorna à rota de cadastro.

PROBLEMA 4

Problema:
Dados corrompidos no localStorage ou o bloqueio do armazenamento pelo navegador podiam interromper a restauração da última rota visitada.

Técnica de diagnóstico:
Inseri um JSON inválido no armazenamento e simulei falhas de leitura e gravação. O console e os testes automatizados localizaram a exceção durante a recuperação.

Solução:
Protegi a leitura, a conversão e a gravação com try e catch. O conteúdo recuperado é validado por versão, estrutura e lista de rotas permitidas. Valores inválidos são descartados e a aplicação volta para a página inicial. O histórico permanece limitado a oito registros e não armazena dados pessoais.

15. REFLEXÃO SOBRE A APRENDIZAGEM

Ao longo do desenvolvimento do Projeto Novo Lar, consegui transformar conceitos estudados em uma aplicação funcional e organizada. No início, meu principal desafio foi compreender como as diferentes partes do JavaScript poderiam trabalhar juntas sem tornar o código confuso. Com a evolução do projeto, passei a enxergar melhor a relação entre estrutura, comportamento e experiência do usuário.

Considero que meus principais pontos fortes foram a organização do código e a integração das funcionalidades. Separei responsabilidades entre navegação SPA, componentes dinâmicos, validação de formulários, persistência de dados, menu responsivo e máscaras de entrada. Também utilizei manipulação do DOM, eventos delegados e um evento personalizado para preparar conteúdos inseridos depois da troca de rota. Essa abordagem permitiu manter as partes independentes e facilitou a identificação de falhas.

Outro aprendizado importante foi perceber que uma aplicação não deve funcionar apenas no cenário ideal. Por isso, preparei validações visuais, tratamento de dados inválidos no localStorage e alternativas para quando a biblioteca externa não estiver disponível. Os testes de navegação, formulário, persistência e integração ajudaram a confirmar o funcionamento e mostraram a importância de investigar problemas com método antes de alterar o código.

Apesar dos bons resultados, reconheço oportunidades de melhoria. Quero aprofundar meus conhecimentos em ES Modules, testes automatizados mais completos e integração com APIs reais. Também pretendo desenvolver ainda mais minha capacidade de documentar decisões técnicas de forma curta e acessível para pessoas com diferentes níveis de conhecimento.

Avalio meu desempenho como Excelente não por considerar o projeto perfeito, mas porque consegui aplicar os conteúdos com autonomia, corrigir problemas encontrados e justificar as escolhas realizadas. Essa experiência fortaleceu minha capacidade de dividir problemas complexos em etapas menores, buscar soluções resilientes e desenvolver interfaces pensando tanto na qualidade técnica quanto nas necessidades das pessoas. São competências que levarei para futuros projetos acadêmicos e profissionais.

16. ESTRUTURA DE BRANCHES COM GITFLOW

A partir desta etapa, organizei o repositório do Projeto Novo Lar com um fluxo inspirado no GitFlow. A branch main representa somente versões estáveis e prontas para entrega, enquanto a develop concentra o desenvolvimento contínuo.

Para registrar uma alteração real, criei feature/documentacao-gitflow a partir de develop. Depois da revisão, essa funcionalidade foi integrada novamente à develop por um merge explícito. Quando o conjunto ficou estável, abri release/1.0.0 para os testes finais e a preparação da primeira versão.

Após a aprovação, a release foi incorporada à main, marcada com a tag v1.0.0 e também devolvida à develop, mantendo as duas linhas atualizadas. Caso surja uma falha urgente em produção, a política será criar uma branch hotfix a partir de main, aplicar e testar a correção e depois integrá-la tanto à main quanto à develop. Mesmo trabalhando individualmente, esse fluxo tornou as alterações mais organizadas, rastreáveis e seguras.

Se preferir um servidor local, execute py -m http.server 8000 na raiz e acesse http://localhost:8000/html/index.html. Caso py não esteja disponível, use python -m http.server 8000.

Para preparar a versão de produção, instale Node.js 20 ou superior, execute npm ci e depois npm run build. A build usa esbuild para gerar bundles e minificar CSS e JavaScript, e html-minifier-terser para minificar HTML. Os ficheiros resultantes ficam em dist, acompanhados de um relatório de tamanho. A IMask 7.6.1 continua carregada por CDN. Sem internet, as máscaras não aparecem, mas o formulário e sua validação continuam funcionando.

Para verificar a aplicação, execute npm run test:build e node validacao-contraste/verificar-contraste.js. Depois visite Início, Projetos e Cadastro, teste o menu, os botões, o histórico do navegador, valores válidos e inválidos no formulário e a restauração da última rota. Os resultados da validação HTML estão em validacao-w3c/resultado.txt, os rácios em validacao-contraste/resultado.txt e a redução medida em dist/relatorio-build.txt.

20. ALTERAÇÕES SEMÂNTICAS E WAI-ARIA

REGISTO 1

Elemento modificado ou tag implementada:
header, nav, main e footer

Justificação e impacto na acessibilidade:
Usei landmarks semânticos para separar o cabeçalho, a navegação, o conteúdo principal e o rodapé. Esta estrutura permite que leitores de ecrã identifiquem as áreas da página e avancem diretamente para a informação pretendida.

REGISTO 2

Elemento modificado ou tag implementada:
nav com aria-label e links com aria-current

Justificação e impacto na acessibilidade:
A navegação recebeu um nome acessível e o link da página ativa é marcado com aria-current. Na SPA, esse estado é atualizado em cada mudança de rota, ajudando o utilizador a compreender onde se encontra.

REGISTO 3

Elemento modificado ou tag implementada:
Botões de menu com aria-expanded e aria-controls

Justificação e impacto na acessibilidade:
Os botões do menu principal e do submenu indicam qual elemento controlam e comunicam se estão abertos ou fechados. O JavaScript atualiza aria-expanded após cada interação, tornando o estado percetível para tecnologias de apoio.

REGISTO 4

Elemento modificado ou tag implementada:
section, cartões e aside com aria-labelledby

Justificação e impacto na acessibilidade:
Associei cada bloco relevante ao respetivo título por meio de aria-labelledby. A relação fornece um nome acessível para as secções, os cartões de projetos e o aviso sobre dados, facilitando a compreensão do conteúdo.

REGISTO 5

Elemento modificado ou tag implementada:
Formulário com label, fieldset, legend, aria-describedby e aria-invalid

Justificação e impacto na acessibilidade:
Cada campo possui um label associado. fieldset e legend agrupam dados pessoais, contacto e endereço. Em caso de erro, aria-describedby liga o campo com a mensagem explicativa e aria-invalid comunica a falha.

REGISTO 6

Elemento modificado ou tag implementada:
Mensagens com role alert, role status e aria-live

Justificação e impacto na acessibilidade:
Os erros do formulário usam role alert para anúncio imediato. Mudanças de rota e confirmações usam role status e aria-live polite, oferecendo retorno sem interromper desnecessariamente a leitura.

REGISTO 7

Elemento modificado ou tag implementada:
Ícones decorativos com aria-hidden

Justificação e impacto na acessibilidade:
Corações, setas e outros símbolos puramente visuais receberam aria-hidden true. Assim, os leitores de ecrã ignoram informação decorativa e apresentam apenas os nomes acessíveis dos controlos e conteúdos.

REGISTO 8

Elemento modificado ou tag implementada:
h1 e main com tabindex negativo e ligação para saltar

Justificação e impacto na acessibilidade:
Após a navegação na SPA, o título do novo conteúdo recebe tabindex negativo e foco temporário. A ligação para saltar ao conteúdo permite ignorar o menu e conduz utilizadores de teclado diretamente para o main.

21. COMPONENTES AJUSTADOS PARA TECLADO E LEITORES DE ECRÃ

REGISTO 1

Nome do componente:
Ligação para saltar ao conteúdo

Descrição do ajuste ou problema retificado:
Foi colocada como primeiro elemento focável e só fica visível ao receber foco. Na SPA, ativa o main com tabindex negativo, permitindo ignorar o cabeçalho e chegar ao conteúdo principal sem percorrer todos os links.

REGISTO 2

Nome do componente:
Menu principal e submenu

Descrição do ajuste ou problema retificado:
Os controlos são botões nativos, acionáveis por Enter e Espaço. aria-controls associa cada botão ao menu, aria-expanded comunica o estado e Escape fecha o menu ou submenu, devolvendo o foco ao controlo correspondente.

REGISTO 3

Nome do componente:
Ordem de foco no documento

Descrição do ajuste ou problema retificado:
A sequência do DOM segue atalho, marca, controlos de navegação, links, conteúdo principal e rodapé. Não foram usados valores positivos de tabindex nem reposicionamento visual por CSS, mantendo Tab e Shift Tab previsíveis.

REGISTO 4

Nome do componente:
Indicador visual de foco

Descrição do ajuste ou problema retificado:
Links, botões e campos recebem contorno de 3 px com afastamento e anel de contraste em focus-visible. Nos cartões, focus-within também reforça a borda e a sombra, tornando o foco percetível sem depender do rato.

REGISTO 5

Nome do componente:
Navegação dinâmica da SPA

Descrição do ajuste ou problema retificado:
Após cada mudança de rota, o h1 ou a secção solicitada recebe tabindex negativo e foco programático. A região role status anuncia a nova página, e aria-current identifica o link ativo sem alterar a ordem de tabulação.

REGISTO 6

Nome do componente:
Formulário de voluntariado

Descrição do ajuste ou problema retificado:
Os campos têm label, e fieldset com legend organiza os grupos. No envio inválido, o foco vai para o primeiro campo com erro. aria-invalid e aria-describedby ligam o estado e a orientação ao campo, com anúncio educado por aria-live.

REGISTO 7

Nome do componente:
Alertas e mensagens de estado

Descrição do ajuste ou problema retificado:
O resumo de falhas usa role alert para aviso imediato. A confirmação usa role status, aria-live polite e aria-atomic true. O toast possui botão nativo com nome acessível para encerramento sem depender de clique com rato.

REGISTO 8

Nome do componente:
Imagens e ícones

Descrição do ajuste ou problema retificado:
Imagens informativas possuem texto alternativo, enquanto corações, setas e ícones decorativos recebem aria-hidden true. Isso reduz anúncios repetitivos e mantém a verbalização concentrada no conteúdo e nos controlos.

22. MODOS DE COR E CONTRASTE

ESTRATÉGIA IMPLEMENTADA

Centralizei as cores em variáveis CSS para que os três perfis visuais partilhem a mesma estrutura. O modo claro permanece como padrão. Quando o sistema indica o tema escuro, a regra prefers-color-scheme: dark altera o fundo, as superfícies, os textos, os estados e as bordas sem modificar o HTML. Para quem solicita mais contraste, prefers-contrast: more ativa fundo preto, texto branco, títulos em ciano e foco amarelo. A regra forced-colors: active respeita ainda as cores definidas pelo sistema operativo.

Não foi necessário JavaScript nem armazenamento local, pois a interface acompanha automaticamente as preferências do dispositivo. Também defini cores próprias para o texto dos botões e dos campos de entrada, reforcei as bordas funcionais e tornei a cor dos marcadores de posição explícita. O amarelo nunca comunica um estado sozinho: o foco combina contorno e realce, enquanto as mensagens apresentam texto, ícone ou borda.

Validei os pares com um verificador local que aplica a fórmula de luminância relativa da WCAG 2.1. Os textos normais alcançam pelo menos 4,5:1 e as bordas ou os indicadores visuais superam 3:1. O texto principal atinge 15,73:1 no modo claro, 17,87:1 no modo escuro e 21:1 no perfil de alto contraste.

23. BUILD DE PRODUÇÃO E MINIFICAÇÃO

FERRAMENTA DE BUNDLER E CONFIGURAÇÃO

Utilizei o esbuild 0.25.11, executado por npm run build. O ficheiro scripts/build.js recria a pasta dist, gera um bundle minificado para cada página, minifica o CSS como estilos.min.css e copia as imagens sem as alterar. O html-minifier-terser 7.2.0 minifica os três documentos HTML. As páginas geradas passam a carregar index.min.js, cadastro.min.js ou projetos.min.js, conforme o caso. Cada bundle mantém a ordem dos scripts definida no HTML de origem. A biblioteca IMask 7.6.1 continua a ser carregada externamente por CDN. Os ficheiros fonte permanecem separados em html, css e js para facilitar a manutenção e a avaliação.

PERCENTAGEM DE REDUÇÃO APÓS A MINIFICAÇÃO

Considerando cada ficheiro HTML, CSS e JavaScript apenas uma vez, a build passou de 71638 para 61035 bytes: 10603 bytes a menos, ou 14,80 por cento. Num cenário agregado de uma visita a cada uma das três páginas, em que o CSS partilhado é contado em cada carregamento, o total caiu de 133782 para 99531 bytes, uma redução de 25,60 por cento. Por página, a redução foi de 28,58 por cento em Início, 26,08 por cento em Cadastro e 19,13 por cento em Projetos. As imagens ficaram fora do cálculo por serem copiadas sem minificação. O relatório normaliza os finais de linha para manter a medição igual em qualquer sistema operativo.

DESAFIOS PARA PRESERVAR A LÓGICA

O principal desafio foi preservar a ordem de execução dos módulos, pois a SPA partilha eventos, templates, rotas por hash, localStorage, mensagens WAI-ARIA e APIs públicas entre os scripts. A IMask, carregada de forma assíncrona por CDN, também poderia ficar disponível antes ou depois do bundle. Para evitar falhas, configurei uma entrada separada para cada página, na mesma ordem do HTML de origem. O módulo de integrações verifica se a IMask já existe e volta a iniciar as máscaras no evento load. Após a build, npm run test:build confirma referências, bundles, imagens e redução de tamanho. npm run test:contraste mantém a validação cromática independente.
